## Запуск на Windows

Нужны Windows, работающий Docker Desktop с Linux/WSL2 engine и Python 3.12. Фактически использован host Python 3.12.14, в образе — 3.12.9. Все команды ниже выполняются в PowerShell из папки проекта. Встроенный Kubernetes Docker Desktop не нужен. Если Python 3.12 не установлен, установите его с python.org с включённым py launcher. Существующее окружение на этом компьютере уже подготовлено.

Для нового компьютера рекомендуется 12–15 GiB свободного места. На этом компьютере перед подготовкой было около 8 GiB на C и ранее загруженные слои Docker. Фактические CPU/RAM, размер и свободное место сохранены в evidence/preflight.json, versions.json и final-inventory.json. Чужие контейнеры и образы не удаляются.

    Set-ExecutionPolicy -Scope Process Bypass
    .\scripts\install-tools.ps1
    .\scripts\lab.ps1 setup
    .\.venv\Scripts\python.exe -m unittest discover -s tests -v
    .\scripts\lab.ps1 all

all последовательно выполняет проверки Kubernetes, A, B, условный контроль без перекоса, C, инвентаризацию и отчёт. Полный цикл занимает около часа, первоначальная загрузка образов зависит от сети. Не запускать фазы параллельно. Для работы по частям:

    .\scripts\lab.ps1 check
    .\scripts\lab.ps1 a
    .\scripts\lab.ps1 b -Rps 6
    .\scripts\lab.ps1 control
    .\scripts\lab.ps1 c -Rps 6 -HpaRps 24
    .\scripts\lab.ps1 inventory
    .\scripts\lab.ps1 report
    Start-Process .\report.html

Если results/ содержит выполненную фазу, скрипт откажется её перезаписать. Для новых прогонов сохраните существующую results/ в archive с отдельным именем. Замеры отчёта относятся к включённым расписаниям и логам; автоматическое завершение программы не гарантирует PASS.

Инструменты закреплены: kind 0.27.0, kubectl/Kubernetes 1.32.2, Helm 3.17.2, metrics-server 0.7.2. Инсталлятор проверяет опубликованные SHA-256 бинарных инструментов. Зависимости приложения закреплены с хешами в requirements.lock. Зависимости построения графиков — requirements-report.lock. Кластер называется mlops-andrey11, контекст kind-mlops-andrey11, namespace lab11. Kubeconfig и локальные Helm-файлы находятся в .runtime и не публикуются.

## Что проверяется

- A: ошибочная готовность до прогрева и исправление при одинаковой нагрузке; штатный A→B с длительным потоком, never-ready B, управляемый возврат A, аварийное завершение и восстановление. В A тайм-аут очереди 65 с, клиентский 70 с, grace 90 с. В B/C очередь 30 с.
- B: обычный Service и ClientIP, равномерный трафик и 80% запросов через client-0. Четыре Pod с разными IP, три повтора каждой комбинации, по 120 секунд поступления запросов. Кеш перед повтором пуст, backend прогрет; соединение закрывается после запроса.
- C: вычислительный стимул HPA 2→3→2, горячий ClientIP после масштабирования, pending/firing/recovery двух алертов. Вход work=8 для HPA и алерт-стимула, work=4 для горячей фазы C; B использует work=1. Фазы B/C не выдаются за прямое сравнение при одинаковой вычислительной стоимости.
- Проверки: холодная готовность, версия после отката, восстановление артефакта и истории после замены Pod, изоляция диалогов, отказы и оборванные потоки. Локальные тесты отдельно подтверждают сохранение /generate и отказ при подмене файла или runtime.

## Просмотр мониторинга

В отдельном PowerShell из корня проекта:

    $env:KUBECONFIG=Join-Path $PWD '.runtime\kubeconfig'
    .\.tools\kubectl.exe --context kind-mlops-andrey11 -n lab11 port-forward svc/grafana 3000:3000

Открыть [Grafana](http://localhost:3000) — dashboard Lab11, анонимный доступ только на чтение. Порты не публикуются в интернет. Для [Prometheus](http://localhost:19090) аналогично port-forward svc/prometheus 19090:9090. Не занимать 19090 во время опытов: его использует наблюдатель.

Сверка клиентского p95 и Histogram автоматически сохраняется в results/B/hot-api-1/reconciliation.json во время B. Повторная сверка до удаления кластера при открытом port-forward Prometheus:

    .\.venv\Scripts\python.exe -m tools.reconcile results/B/hot-api-1

Prometheus ограничен 6 часами/384 МБ, emptyDir 512 MiB. Grafana emptyDir 128 MiB. При удалении кластера временная TSDB исчезает; сохранённые JSONL, buckets, конфигурации и отчёт остаются.

## Удаление собственного стенда

    .\scripts\lab.ps1 cleanup
    docker image rm andrey11-api:1.0.0

Удаляется только кластер mlops-andrey11; образ приложения удаляется второй отдельной командой. Общие образы Python/kind/мониторинга могут использоваться другими работами и автоматически не удаляются. Глобальная очистка Docker не нужна. Сокращение VHDX после удаления не гарантируется.

[Первичный источник](https://cloud.google.com/blog/products/containers-kubernetes/how-gke-inference-gateway-improved-latency-for-vertex-ai). Ограничения CPU-имитатора описаны в отчёте.

С разрешения автора данные Docker Desktop перенесены на D:/DockerDesktopData/DockerDesktopWSL штатной настройкой приложения. Это изменение локального окружения; для повторения на другом компьютере перенос не требуется при достаточном месте. Исходная остановка setup из-за нехватки места сохранена в evidence/setup-before-storage-fix.log.

Сеть kind использует kubeProxyMode=nftables: в установленном ядре WSL 5.15.167.4 отсутствует xt_recent, поэтому iptables-реализация ClientIP не могла применить правила. Исходный лог и конфигурация сохранены в evidence/. Настройка относится только к учебному кластеру.

После основного B дополнительно выполнен условный контроль tools/control.py: при том же равномерном расписании намеренно выбирается раскладка ClientIP 2+2 через эквивалентные временные Service. Все попытки сохранены, исходные три повтора не заменяются. Контроль показывает отсутствие перегруза при благоприятной раскладке, а не общую гарантию балансировки. Результаты — results/controls/.

Системные логи kind сохранены с короткими именами для переносимости Windows; evidence/kind-logs/path-map.json связывает каждый файл с исходным путём и SHA-256. Содержимое логов не изменялось.
